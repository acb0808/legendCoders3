## 구현 범위
1. 코드, 입력 JSON, 허용 패키지 세트, 자원 예산, 시드, 기대 출력 스키마를 요청 계약으로 정의한다.
2. 상태를 COMPLETED, CODE_ERROR, TIMEOUT, POLICY_VIOLATION, INFRA_ERROR로 구분한다.
3. 애플리케이션 비밀 설정 타입을 요청 계약에서 참조할 수 없게 한다.
4. 로컬·운영 샌드박스 구현을 교체 가능한 provider로 둔다.

## 테스트 우선 실행 순서
1. 첫 필수 테스트를 작성하고 해당 테스트만 실행한다.
2. 의도한 이유로 실패하는지 확인한다.
3. 테스트를 통과시키는 최소 구현을 작성한다.
4. 모듈 전체 테스트와 관련 통합·보안 테스트를 실행한다.
5. 정적 검사 후 증거와 운영 문서를 갱신한다.

## 필수 테스트와 판정 기준
- [ ] **T03.1-CT1:** 유효 요청과 결과가 JSON 직렬화 왕복 후 동일하다.
- [ ] **T03.1-CT2:** API 키·DB URL·호스트 경로 필드를 요청에 넣을 수 없다.
- [ ] **T03.1-CT3:** 시간 초과와 인프라 오류가 서로 다른 상태로 매핑된다.
- [ ] **T03.1-CT4:** 잘못된 결과 스키마는 ValidationEvidence로 승격되지 않는다.
- [ ] **T03.1-CT5:** provider 교체가 오케스트레이터 코드를 바꾸지 않는다.

## 작업 완료 정의
- [ ] 위 테스트가 모두 통과한다.
- [ ] 실패 테스트가 구현 전 실제로 실패함을 확인했다.
- [ ] 실패·판단 불능 상태가 구조화된 코드로 기록된다.
- [ ] 관련 회귀·정적 검사가 통과한다.
- [ ] 로그에 비밀정보와 불필요한 원문 전체가 노출되지 않는다.
- [ ] 범위 밖 기능을 추가하지 않았다.
